# 醒来的时候，他在

一个第一人称乙女游戏。没有写好的剧本 —— 默认由 Gemini / Nano Banana 现场生成
静帧故事，也可以打开视频模式交给 [fal](https://fal.ai) 上的 **MiniMax H3 Max**。

睁眼之前，你先挑一种画风，再写下今天想和他做点什么。你写下的，就是这一天真正会发生的事。

画风三选一：**日系动画** / **3D 动画** / **写实电影**。它不是滤镜 ——
它被写进这一局的每一个提示词里，连他的立绘都为这个画风单独画一张。

## 玩法

```
挑画风 + 写下你的愿望 ──► 第一幕（醒来）其实已经在你打字时开拍了
      │                                │
      ▼                                ▼
 愿望被写成一个镜头              第一幕播放
      └──► 在这段播放里拍完 ──► 播放 ──► 自动推进 / 关键二选一 / 自由回答 ──► 循环
```

**等待永远是别人的时间。** 这是整个设计里唯一的一个想法，从
[LAST FRAME](https://github.com/blendi-remade/interdimensional-game) 继承过来，
收窄到一条分支上：

- 你在挑画风、打字的那十几秒，付掉了他的立绘、开场画面和第一幕十秒视频的生成时间；
- 第一幕在屏幕上播放的十秒，付掉了你那个愿望的生成时间；
- 关键选择和自由回答之后才生成对应画面；没有重要决定的过程由故事自动推进，
  当前旁白会覆盖这段生成时间。

## 他为什么一直是他

视频模型没有记忆。h3 每次调用只看得见这一次的提示词和这一次的参考图，
所以"同一个人"必须每一帧都重新证明一次。这件事由两样东西撑着：

1. **一张立绘**。`/api/portrait?style=…` 每种画风第一次用到时画一张，存到
   `.cache/portrait-<画风>.jpg`，之后每一局都从磁盘读同一张。它作为
   `reference-to-video` 的 **Image 2** 参与每一个镜头。三种画风用**同一个
   随机种子**，所以出来的是同一个人的三种画法，而不是三个人。
2. **同一句英文外貌描述**，一字不差地写进每一个提到他的提示词里 ——
   让画面和文字永远不打架。

用的是 `minimax/h3-max/reference-to-video` 而不是 `image-to-video`：
ref2v 是"从参考图构图"而不是"从关键帧续拍"，握房间握得松一点，
但握人握得紧得多。在恋爱游戏里，沙发挪了位置可以原谅，脸变了不行。

## 提示词是怎么写的

镜头提示词的结构是照着 MiniMax 自己那套来的，不是随手写的散文：

```
[Static shot] + 第一人称前导 + 动作（2~3 拍） + 负面守卫 + 声音 + 画风
```

- **动作放在最前面，用动词开头。** H3 对动词的权重最高 ——
  "leans in and rests his forehead against hers" 比 "He is leaning in" 强得多。
- **一个镜头拆成两三拍**，用 first / then / as 连起来。
  只描述一个"状态"，模型没有东西可动；给它两拍，它才拍得出一个镜头。
- **40~80 词。** 上限 480 字符，整条提示词上限 1900（H3 大约 2000 就整条拒绝）。
- **说环境怎么反应** —— 被子被带动、光在他脸上移动、热气偏了。
  H3 靠这些决定东西怎么动。
- **方括号镜头指令**：`[Static shot]` `[Push in]` `[Pan left]` `[Tilt down]`
  `[Shake]` `[Tracking shot]` 等，一个括号里最多三个（同时发生），
  分开写就是先后发生。这是 Hailuo 系列的官方语法，**H3 没有明确文档说支持** ——
  留着是因为不支持的话它也只会被当成一句普通的镜头提示。
  想做 A/B，把 `lib/character.ts` 里的 `SHOT_TAGS` 改成 `false`。

**第一人称靠的不是"说它是第一人称"。** 光靠文字压不住，模型会退回旁观视角
（我们实测踩过两次：它把你自己的后脑勺塞在前景角落）。真正管用的是三样：

1. **画面高度**写清楚（"camera at her eye height"、"pillow height"）；
2. **近景下方有实体锚点** —— 她自己的手、被子边缘。没有锚点，模型不知道该把
   观众放在哪儿；
3. **负面守卫放在动作后面**，而且只写真的翻过车的那几条。
   以前这一坨写在最前面、又长又全，结果是"这是第一人称"最后才被读到，
   动作本身被一堆约束淹掉。

**开场那一幕**用的是 POV 教程里对"醒来"的标准做法：
眼睑一样的黑边从上下退开，配合 **rack focus 从完全虚到实**。
只写 "she wakes up" 是没用的 —— 模型没有东西可以动，于是它去动他，醒来根本不会发生。

## 关键决定

- **画面是唯一的事实。** h3 不会照着提示词演，它演一个相邻的东西。
  讲述者（Gemini）读的是刚播完那十秒里抽出的三帧，写的是**画面上真的发生了什么**，
  不是提示词写了什么。否则文字和画面三幕之内就会分家。
- **选项自带镜头提示词。** 每张卡片在上一段视频还在播的时候，就已经把
  自己那一幕的英文提示词写好了。所以点一下卡片，零个 LLM 调用，直接开拍。
- **他不在画面里说话。** h3 会生成配音，而在没指定台词时它会胡乱哼一种
  听不出是中文还是日文的伪语言，一段温柔的戏就毁了。所以每个镜头都显式声明
  "只有环境音和钢琴"，他的话以屏幕文字给出 —— 这本来也是这个类型的惯例。
- **中文界面，英文提示词。** 玩家可以随便用中文写，Gemini 负责翻译成镜头。
  h3 和 nano-banana 对中文提示词的构图和风格保持明显更差，而玩家永远看不到提示词。
  他的中文名只出现在他自己的台词里 —— 英文提示词里他永远是 "the young man"，
  因为视频模型读不懂中文名，写进去只是挤掉本该用在他脸上的细节。
- **故事规划使用 Gemini 3.8 Flash。** 审核和选角仍可沿用环境中配置的低成本模型；
  剧情、台词、交互方式和下一幕提示词使用低思考级别的 3.8 Flash，以提高中文自然度和
  结构化输出稳定性，又避免推理吃掉短 JSON 的输出预算。
- **交互由讲述者判断。** 只有会改变后续的具体决定才显示两个不同选项；感受、题字、
  承诺等必须由玩家亲口回答的问题只留自由输入；搅拌、烘烤、等待等普通过程自动推进。
  不再为了让界面一直有卡片而编造无关选择。
- **横屏。** h3 出的每一段都是 16:9，所以画面被放进一个真正的 16:9 框里加黑边，
  而不是裁切填满窗口 —— 第一人称游戏里，构图本身就是状态，裁掉两边等于裁掉剧情。
- **打开页面不花钱。** 生成从你第一次点画风或第一次敲键盘时才开始。
  在你选好画风之前，没有一个"正确的开场"可拍。

## 跑起来

```bash
npm install
npm run dev
```

`.env.local`：

| 变量 | 用途 |
| --- | --- |
| `FAL_KEY` | **只有 h3-max 视频**。别的什么都不走这个键 |
| `GEMINI_API_KEY` | 讲述者、愿望改写、选角、审核（文本，AI Studio key 够用） |
| `GOOGLE_IMAGE_API_KEY` | 所有静帧。要开了账单、放开了 Vertex AI API 的 key |
| `GOOGLE_CLOUD_PROJECT` | 填了走 Vertex，留空走 Gemini API |
| `IMAGE_PROVIDER` | 用哪个图像模型。不填的话，见下 |

全部只留在服务端 —— `FAL_KEY` 走 `@fal-ai/server-proxy`，
视频走同源的 `/api/media` 代理，这样 `<canvas>` 抽帧不会被 CORS 挡掉。

## 图像模型是可换的

**fal 在这个项目里只负责视频。** 所有静帧 —— 立绘、开场画面、无视频模式的每一幕 ——
都从 [`lib/imagegen.ts`](lib/imagegen.ts) 这一个口子出去。以前它们是 nano-banana，
而且散在三个路由里各写各的 URL、重试和超时，"换个图像模型"意味着改三个文件
还得指望它们保持一致。现在换模型就是改这一个文件。

一个图像提供方必须能做两件事：

- **生成** —— 提示词 → 一张图；
- **编辑** —— 提示词 + 多张参考图 → 一张图。

**编辑这半边不是可选的，而且是更难的那半边。** 整个游戏靠它：
他每种画风的立绘是把他那张原图**重画**一遍（一句话复现不了一张脸）；
开场画面是**从他的立绘**构出来的；无视频模式的每一幕是"上一帧 + 他的立绘"的编辑。
一个只能文生图的提供方，会让他每一幕都是另一个人。**先确认多图编辑能力再接。**

### `google` —— nano banana（默认，用 API key）

`gemini-3.1-flash-image`（Nano Banana 2），走 Google 自己的平台，不经过 fal。

Vertex 和 Gemini API **请求体完全一样**，只有 URL 和鉴权头不同，所以代码里也只分这两处：

- 填了 `GOOGLE_CLOUD_PROJECT` → Vertex，按项目、按区域
  `https://{LOC}-aiplatform.googleapis.com/v1/projects/{PROJ}/locations/{LOC}/publishers/google/models/{MODEL}:generateContent`
- 没填 → Gemini API，只认 key
  `https://generativelanguage.googleapis.com/v1beta/models/{MODEL}:generateContent`

鉴权用 `x-goog-api-key`，和 Maps key 是同一种东西 —— **实测 Vertex 端点接受 API key**。
没有 key 而有项目时，回落到 ADC（`GOOGLE_APPLICATION_CREDENTIALS` 的服务账号
或 `gcloud auth application-default login`）。

**用 API key 走 Gemini API，控制台上要做三件事**（都是设置，不是代码）：

1. 项目里**启用 Generative Language API**（`generativelanguage.googleapis.com`）；
2. 那个 key 的 **API restrictions 里加上 Generative Language API** ——
   这两件是**分开的两层**：启用了但 key 没放开，报 `API_KEY_SERVICE_BLOCKED`；
   key 放开了但没启用，报 `has not been used in project ... before or it is disabled`。
   两条错误长得像，其实是不同的开关；
3. 项目**开账单**。图像模型免费额度是 `limit: 0`，不开账单一定 429。

然后把 key 填进 `.env.local` 的 `GOOGLE_IMAGE_API_KEY`。

**Vertex 是可选的，多数情况下不需要。** 它唯一的门槛是：
**Vertex 完全不收 API key，只收 OAuth。** 要用就得建 service account
（角色 Agent Platform User，`roles/aiplatform.user`）、下载 JSON、设 `GOOGLE_APPLICATION_CREDENTIALS`，
代码会自动优先走它。除非你要企业配额、项目内计费或数据驻留，否则 Gemini API 就够。

### 选哪个

`IMAGE_PROVIDER` 不填时：有 Google 的 key 就走 `google`，
没有就报一个说清楚该干什么的错，**绝不会退回 fal**。

要接新的：写一个 `(ImageRequest) => Buffer` 的函数，加进 `PROVIDERS`，
设一下 `IMAGE_PROVIDER`。就这些。

## 选角：做一个你自己的男主

第一页上那张脸，点一下就打开选角。两条路，通向同一个地方 ——
因为人坐下来的时候手里通常只有这两样东西：他的一张图，或者他的一个念头。

- **写一个** —— 用中文描述他。Gemini 把它写成那句每个镜头都要带的英文外貌描述，
  nano-banana 照着画出立绘。一次 Gemini + 一次 nano-banana，约 $0.04。
- **传一张** —— 上传一张图。**这张图就是他**：Gemini 只负责把它读成文字，
  因为管线的文字那一半看不见图片。免费。

上传这条路值得说清楚：他的脸**不会**被从一句话里重新想象一遍。原图会被保留，
然后按你选的画风重画（见 `restylePrompt`）。所以传一张照片、选日系动画，
你得到的是"那个人的动画版"，而不是"一个符合描述的陌生人"。

做好之后会把**那句英文外貌描述**一起显示出来 —— 它是要跟着每一个提示词跑一整局的，
不对劲的话，这时候发现比第三幕才发现便宜得多。

存在 `.cache/cast/<id>/`。内置的沈砚不落盘，他是代码，
所以再糟的自定义角色也锁不死这个游戏。

## 改内置的他

他写在 [`lib/character.ts`](lib/character.ts) 的 `DEFAULT_HIM`：
名字、外貌、性格、开场的房间、第一帧、第一个镜头都在这一个文件里。
改完 `descriptor` 之后访问一次 `/api/portrait?style=anime&refresh=1` 重画立绘，
或者直接删掉 `.cache/` 里对应的文件。

三种画风写在 [`lib/styles.ts`](lib/styles.ts)，加第四种只需要在那里多写一条。

## 无视频模式

右上角的开关。开了之后，每一幕不再由 h3 拍成十秒视频，而是由 nano-banana
画成一张独立静帧。只传他的立绘保持身份，不把上一幕当成编辑底图；地点、光线和
构图由每一幕的完整提示词重新描述。

- **便宜大约十倍**，而且几秒就到，不是几分钟。
- 讲述者读的是那一张静帧而不是三帧，其余一模一样 —— 它本来就被要求
  "只描述你看得见的东西"，静帧同样成立。
- **可以中途随时切**。静帧和视频最后都只留下一帧，而下一幕只继承那一帧，
  所以两种模式能无缝接在一起，不用重开。

想调剧本、调选项、调他的性格的时候用这个模式，别烧视频钱。

## 花费

每一幕 = 1 次 h3-max（10 秒 768P）+ 1 次 Gemini。
无视频模式下 = 1 次图像生成 + 1 次 Gemini。
开场额外一次图像生成；立绘每种画风只做一次，之后永久复用。

- 打开页面本身不产生任何调用。
- **第一次交互**（点画风 / 敲第一个字）会开始生成开场。
- 开场生成开始之后再换画风，会作废重来 —— 画风是烤进立绘和开场静帧里的，
  换不掉，只能重拍。

## 结构

```
lib/character.ts   他（DEFAULT_HIM），以及每个镜头都继承的语法（镜头、声音）
app/api/cast       选角：写一个 / 传一张，都落到同样的立绘 + 英文外貌描述
components/creator.tsx  选角界面
lib/styles.ts      三种画风。每一个提示词的结尾
lib/story.ts       讲述者：读画面 -> 中文旁白 + 自动推进 / 两个关键选项 / 自由回答
lib/engine.ts      导演：整个循环、预生成、状态快照
lib/fal.ts         h3 客户端。fal 在这里只有视频
lib/imagegen.ts    图像模型的唯一出口。换模型改这一个文件
lib/frames.ts      从播完的片子里抽首帧/中帧/尾帧
app/api/portrait   立绘：每种画风从原图编辑一次，存磁盘，之后永远复用
app/api/fal/proxy  FAL_KEY 不进浏览器
app/api/media      同源视频代理，为了抽帧不被 CORS 挡
```
